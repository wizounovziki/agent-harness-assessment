# ReAct 与运维业务的结合

日期：2026-11-12

## 1. 设计定位

ReAct 将推理与任务行动交替组织，利用外部反馈更新后续决策。[原始论文](https://arxiv.org/abs/2210.03629)

本项目以此组织模型与工具的循环；运维场景提供目标、服务目录、Runbook、SEV 规则和完成条件；Harness 负责批准、校验、预算、持久化和副作用控制。

| ReAct 环节 | 在本项目中的含义 | 运维示例 |
| --- | --- | --- |
| Reason / 推理 | 根据目标、历史观测和业务策略决定下一步；保存可见的决策摘要与动作依据 | 服务状态未知，先查询 payment；已观察到异常，检索对应处理手册 |
| Action / 行动 | 提出工具名和参数，由 Harness 验证并执行 | 调用 get_service_status、search_knowledge_base；形成 create_incident 草案 |
| Observation / 观察 | 将通过校验的工具结果或结构化错误回填上下文 | payment=degraded、Runbook 内容、查询超时、事件编号 INC-001 |

模型通过下一轮观测决定继续查询、修正动作或形成最终报告。示例中的工具顺序用于展示一条路径；运行时依据实际反馈推进。

## 2. 业务约束如何进入循环

1. 目标与完成条件：完成服务检查；报告引用工具证据；声明已创建事件时须存在对应事件编号。
2. 业务上下文：服务目录定义有效服务；Runbook 提供处理建议与严重程度依据；SEV 枚举和字段约束由可信配置定义。
3. 动作范围：三个注册工具构成可用行动集合，工具输入输出和业务规则由网关验证。
4. 写入审批：创建事件的具体标题、描述和严重程度绑定为待审批动作；用户有效批准后执行原参数。
5. 错误反馈：可确认的工具失败转换为 Observation；模型可以选择修正、补充查询或报告不足。
6. 运行约束：每次实际模型请求和工具尝试均检查预算；暂时错误有限重试，格式错误有限修复，累计用量跨审批恢复保存。
7. 未知副作用：创建请求超时先按幂等键确认；仍无法确认时进入 needs_review。

## 3. 演示样例

目标：检查 payment，必要时创建故障事件。

| 轮次 | Reason 的决策摘要 | Action | Observation |
| --- | --- | --- | --- |
| 1 | 需要先取得当前状态 | get_service_status(payment) | payment=degraded |
| 2 | 需要取得对应处理规则 | search_knowledge_base(payment Runbook) | 示例手册将该场景映射为 SEV2，并建议记录事件 |
| 3 | 已有状态与手册依据，提交事件草案 | create_incident 草案 → 等待批准 | 用户有效批准后执行，取得 INC-001 |
| 4 | 业务检查与已批准写入均有结果 | 生成最终报告 | 报告引用服务状态、手册和事件编号 |

场景中的 SEV2 为演示数据中的规则。实际严重程度依据该场景的配置和手册决定。
